# Глава 7. Хранение данных

> **Цель главы:** сделать так, чтобы данные переживали перезапуск сервера, не портились при сбоях и не терялись при работе из двух вкладок/устройств.

---

## 7.1 Где хранить данные домашнего проекта

Варианты и трезвый выбор:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| PostgreSQL/MySQL | Мощь, запросы | Ставить, настраивать, порты, пароли | Слишком много для домашней доски |
| SQLite | Файл + SQL | Нужна библиотека (нативная сборка) | Хорош, но не «ноль зависимостей» |
| **JSON-файл** | Ноль зависимостей, читается глазами, бэкап = копия файла | Нет запросов, весь документ в памяти | ✅ Выбор NeuroBoard |

Правило проекта: **один файл — одна фича**. `data/db.json` — доска; `data/movies.json` — фильмы; `data/notify.json` — уведомления. Так сбой в одной фиче не портит остальные, а бэкап — это просто копирование папки.

> Когда JSON-файл станет плох: если записей десятки тысяч и нужны выборки по условиям. Для домашней доски (сотни карточек) — идеально.

## 7.2 Схема `data/db.json`

Реальная структура доски (сокращённо):

```json
{
  "board": {
    "columns": [
      { "id": "c1", "title": "Задачи", "color": "#f5b7b1" },
      { "id": "col_muiv9nt9", "title": "Закупки", "color": "#f9e79f" }
    ],
    "cards": [
      {
        "id": "card_mubj0bzl",
        "columnId": "c1",
        "title": "STM32",
        "text": "задеплоить линукс…",
        "priority": "",
        "due": ""
      }
    ]
  },
  "events": [],
  "settings": {
    "clock": true,
    "background": { "type": "image", "src": "/uploads/up-….jpg", "blur": 3, "darken": 40, "adapt": true }
  },
  "layout": { "movies": {...}, "news": {...}, "notif": {...} },
  "_tombstones": { "cards": {}, "columns": {}, "events": {} }
}
```

Принципы проектирования схемы:

1. **`id` у всего.** Никогда не полагайтесь на позицию в массиве — только на `id` (`card_mubj0bzl`, `c1`). Id генерируется функцией `uid()`:
   ```js
   function uid(p = '') {
     return p + Date.now().toString(36) + Math.random().toString(36).slice(2, 8);
   }
   ```
   Время в base36 + случайный хвост = уникально на практике и сортируется по времени.
2. **Связи через id.** Карточка не «лежит в колонке», а хранит `columnId`. Колонки и карточки — два плоских массива. Так проще искать, перемещать, удалять.
3. **Настройки отделены от данных.** `settings.background`, `settings.clock` — это «как выглядит», а не «что за задачи».
4. **Служебные ключи с подчёркиванием** (`_tombstones`, `_aiMode`) — «не показывать пользователю, не отдавать наружу».

## 7.3 Запись без порчи файла: tmp + rename

Наивная запись таит катастрофу:

```js
// ❌ ТАК ДЕЛАТЬ НЕЛЬЗЯ
fs.writeFileSync(DB_FILE, JSON.stringify(db));
```

Если питание выключится в середине — на диске останется **обрезанный JSON**, и доска больше не загрузится. Правильный приём — «запись рядом + переименование», которое на диске атомарно:

```js
function saveDb() {
  fs.mkdirSync(DATA_DIR, { recursive: true });
  const tmp = DB_FILE + '.tmp';
  fs.writeFileSync(tmp, JSON.stringify(db, null, 2));  // 1) пишем во временный файл
  fs.renameSync(tmp, DB_FILE);                          // 2) мгновенно заменяем основной
}
```

Именно так в `server.js:96`:

```js
function saveDb() {
  const tmp = DB_FILE + '.tmp';
  try {
    fs.writeFileSync(tmp, JSON.stringify(db, null, 2));
    fs.renameSync(tmp, DB_FILE);
  } catch (e) {
    console.error('saveDb failed:', e.message);
    try { fs.unlinkSync(tmp); } catch (e2) {}   // подчистить мусор
  }
}
```

`JSON.stringify(db, null, 2)` — ещё и форматирует с отступами: файл можно открыть и прочитать глазами. Это сознательный выбор в пользу человекочитаемости (для домашнего проекта важнее размер ~2 КБ, чем микросекунды).

**Задача 7.2.** Смоделируйте сбой: напишите скрипт, который пишет в файл 1000 раз и на 500-й бросает ошибку. Сравните два варианта: прямую запись и tmp+rename. В первом случае файл бьётся, во втором — всегда валиден.

## 7.4 Чтение с защитой

```js
let db = defaultDb();                 // 1) всегда есть «значение по умолчанию»
try {
  if (fs.existsSync(DB_FILE)) {
    db = JSON.parse(fs.readFileSync(DB_FILE, 'utf8'));
  }
} catch (e) {
  console.error('db.json not read, using defaults:', e.message);
}
saveDb();                             // 2) сразу создаём/перезаписываем файл
```

Правила:

1. **Никогда не падать при старте.** Нет файла / битый JSON → берём дефолт и продолжаем.
2. **defaultDb()** показывает, как должна выглядеть пустая доска.
3. После загрузки сразу `saveDb()` — файл существует, схема гарантированно записана.

Это настоящий код `server.js:72–76`.

## 7.5 Полная замена документа: PUT и его проблемы

Самый простой способ синхронизации — «клиент присылает **всю** доску, сервер её сохраняет»:

```js
if (p === '/api/data' && (req.method === 'PUT' || req.method === 'POST')) {
  const body = JSON.parse((await readBody(req)).toString() || '{}');
  db = mergeSave(body);
  saveDb();
  return json(res, 200, { ok: true, db: publicDb() });
}
```

Клиент (`app.js:49`) отправляет `this.db` целиком на **каждое** изменение. Это удобно: не надо придумывать REST для каждой мелочи. Но рождает две проблемы:

### Проблема 1: гонки (два устройства)

ПК прислал доску версии A, телефон — версии B (без кнопки, созданной на ПК). Если просто записать последнее — одна из правок **потеряется**.

### Проблема 2: «воскрешение» удалённого

Удалённая карточка не приходит в новом PUT. Но если придёт запрос от **устаревшего** клиента (где карточка ещё есть) — она снова появится.

### Решение проекта: слияние + «надгробия»

`mergeSave()` (`server.js:147`) не перезаписывает, а **сливает** текущее состояние с присланным:

- карточки/колонки/события объединяются **по id** (присланная запись заменяет старую с тем же id);
- удаления приходят явным списком `_deleted: { cards: [...], columns: [...] }`;
- удалённый id попадает в `_tombstones` и **не может вернуться**, даже если кто-то пришлёт его снова.

Упрощённая версия того же принципа, чтобы понять идею:

```js
function mergeList(curArr, incArr) {
  const out = new Map();
  for (const x of curArr) if (x && x.id) out.set(x.id, x);  // что было
  for (const x of incArr) if (x && x.id) out.set(x.id, x);  // что прислали (приоритет)
  return [...out.values()];
}
```

Плюс уборка старых надгробий, чтобы файл не рос бесконечно (`pruneTombstones`):

```js
const MAX = 800, AGE = 30 * 24 * 3600 * 1000;   // 30 дней
for (const k of Object.keys(m)) if (now - m[k] > AGE) delete m[k];
```

> 💡 Не обязательно повторять это в своём проекте. Но **знать про такую проблему** нужно: как только появятся «два клиента и полная перезапись» — ждите сюрпризов. Для домашней доски частый и достаточный компромисс — `mergeList` по id.

**Задача 7.3.** Добавьте в свой мини-канбан (глава 6) `PUT /api/data`, но с слиянием по id, как выше. Проверьте: удалите карточку через DELETE, затем пришлите старый `GET /api/data` в PUT — карточка **не** должна вернуться. (Для этого понадобится хотя бы простой `_deleted`.)

## 7.6 Когда файл большой: дебаунс и «горячая» память

Файл уведомлений `notify.json` — 120 КБ и обновляется на каждое уведомление. Писать на диск при каждой летящей SMS — тормоза. Решение из `notify.js:66`: **держать в памяти, а писать раз в 1.5 секунды**:

```js
let saveTimer = null;
let saveDirty = false;

function scheduleSave() {
  saveDirty = true;
  if (saveTimer) return;                       // уже запланировано
  saveTimer = setTimeout(() => {
    saveTimer = null;
    if (saveDirty) { saveDirty = false; saveHistory(); }  // одна запись вместо сотни
  }, 1500);
}
```

Уточните, что теряется: если процесс убьют в эти 1.5 с — потеряются последние уведомления. Для уведомлений это допустимо, для доски — нет (поэтому доска сохраняется сразу). **Каждая фича выбирает свой компромисс «скорость ↔ надёжность».**

Ещё приём: **история в памяти, а на диск — срез**. События умного дома живут кольцом в памяти (последние 100), не персистятся вовсе (`AGENTS.md`). А `busyScenes` (защита от зацикливания сцены) специально **не** сохраняется — иначе после перезапуска сцена «залипнет» навсегда.

**Задача 7.4.** Реализуйте `scheduleSave` для своего мини-канбана и проверьте логами: при 10 быстрых добавлениях карточек должна быть **одна** запись на диск.

## 7.7 Служебные файлы вокруг данных

| Файл | Роль | Особенность |
|---|---|---|
| `data/db.json` | Доска | атомарная запись, слияние |
| `data/notify.json` | История уведомлений (500 шт.) | дебаунс, фильтр приватности |
| `data/news*.json` | Кэш новостей и оценки | пересоздаётся при fetch |
| `config.json` | Настройки + **секреты** | в `.gitignore`, не отдаётся по сети |
| `data/yandex-token.txt` | OAuth-токен | `mode 600` (только владелец) |
| `uploads/` | Картинки/звуки | проверка префикса пути при отдаче |

Обратите внимание: **токен Яндекс Станции хранится в `data/`, а не в `config.json`** — и файл создаётся с правами `600`. Это осознанная гигиена секретов.

## 7.8 Бэкап и восстановление

Простейший надёжный бэкап:

```bash
# снимок всей папки данных с датой в имени
tar czf ~/kanban-backup-$(date +%F).tgz -C ~/kanban-board data config.json

# восстановление
tar xzf ~/kanban-backup-2026-10-20.tgz -C ~/kanban-board
```

Ещё лучше — автоматически по крону каждый день:

```bash
crontab -e
# 0 4 * * * tar czf ~/kanban-backup-$(date +\%F).tgz -C ~/kanban-board data config.json
```
